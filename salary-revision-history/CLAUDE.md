# salary-revision-history/

Two-stage salary-revision approval workflow: HR submits proposed revisions, a designated approver marks them approved/rejected, and approved rows move into permanent history. See root [CLAUDE.md](../CLAUDE.md) for cross-cutting principles.

**Correction to root CLAUDE.md**: the root file names "Zafar sir" as the authorizing signatory requiring a physical signature. Nothing in this module's code references that — approval here is purely email-based (`nazneen@butlerleather.com` is the in-system approver). If "Zafar sir" sign-off is a real requirement, it's an out-of-system step not enforced anywhere in this code; don't assume it's technically gated.

## Files

- `Menu button` — `onOpen(e)` / `addHrPayrollMenus_()`: menu items "Submit for Approval" → `submitForApproval()`, "Revision Approval" → `revisionApproval()`.
- `Submit_Approval` — `submitForApproval()` (gated entry) → `submitForApprovalCore_(bypassTabGuard, ssOverride)`. Must run from the `HR_UPDATE` tab. Requires `ID.NO, BASIC, DA, HRA, CONV.ALL, SPL.ALL, EFFECTIVE_FROM [MM/DD/YY], REVISION_TYPE, SUBMIT_STATUS, OLD GROSS` all present (`OLD GROSS` added for the guardrail below). Copies eligible rows into `REVISION_APPROVAL`, clears only `ID.NO, REVISION_TYPE, PLANNED GROSS, EFFECTIVE_FROM [MM/DD/YY]` from source, emails an HTML summary to `nazneen@butlerleather.com` (reply-to `hrassist@butlerleather.com`, subject `Salary Revision Approval Request [SR-APPROVAL]`, threaded via `Re:` + `GmailApp.search`). Deliberately avoids Gmail reply/replyAll to keep `hrassist` out of To/CC on approval threads.
  - **Guardrails (added)**: two extra checks run per row, on top of required-fields + `SUBMIT_STATUS = OK`, before a row is allowed into `REVISION_APPROVAL`. (1) *Duplicate Aadhaar, active elsewhere* — looks up the row's `ID.NO` in Employee Master; if another `ID.NO` shares the same `AADHAAR NO` and is `STATUS = ACTIVE`, the row is blocked (this is the reissued-employee-code scenario: HR raised a new code without inactivating the old one). (2) *Increment with no baseline* — if `REVISION_TYPE = "Increment"` and `OLD GROSS` is blank/0, blocked with a message to resubmit as `"Salary Fixation"` instead. Blocked rows are excluded from `outRows`/append/clear and stay untouched in `HR_UPDATE` for HR to fix — same as today's ineligible rows.
  - `_fetchEmployeeMasterIndex_()` — new helper in this file, reads Employee Master via the Sheets Advanced Service (same spreadsheet ID `1yqQ-edwQzZd0pAlaXCAAZt88MbsHfCf4hCcxti4ojCw`, GID `1874110664`, mirroring `attendance/07_EmployeeMaster_Fetch.gs`'s pattern including its 6h title cache). Returns `ID.NO → {status, aadhaar, name}`. This is a **new cross-spreadsheet dependency** — the module had none before. Requires the Sheets Advanced Service ("Sheets API") enabled on this project (Extensions > Apps Script > Services). Also called directly from `Revision_Approval` (same Apps Script project, no duplication needed).
  - `submitForApprovalCore_` now **returns** `{ submittedCount, skippedCount, blocked: [{idNo, name, reason}] }` from every exit point (previously returned nothing).
- `Revision_Approval` — `revisionApproval()` (gated entry) → `revisionApprovalCore_(bypassTabGuard, ssOverride, approverOverride)`. Must run from `REVISION_APPROVAL` tab. Reads `APPROVAL_STATUS` values `APPROVED`/`REJECTED`. Approved rows append to `REVISION_HISTORY`, stamped `APPROVED_BY`/`APPROVED_ON`, new row set `ACTIVE_FOR_PAYROLL = ACTIVE` while flipping the prior matching row to `IN-ACTIVE`. Rejected rows append to `REJECTED_HISTORY`. Processed rows deleted **entirely** from source bottom-up (whole row, every column — not a partial clear).
  - **Guardrail (added)**: an `APPROVED` row is held back (excluded from this run, stays untouched in `REVISION_APPROVAL`) when `REVISION_TYPE = "Salary Fixation"` **and** the employee's Aadhaar (via `_fetchEmployeeMasterIndex_()`) already appears in `REVISION_HISTORY` under a *different* `ID.NO` with `ACTIVE_FOR_PAYROLL = ACTIVE` — i.e. a reissued code whose old salary history hasn't been manually verified yet. The hold releases once a human sets `OLD_SALARY_STATUS = CHECKED` on that row. `REJECTED` rows are never held (no downstream salary risk). New required columns: `REVISION_TYPE` + `OLD_SALARY_STATUS` (last column, manual) on `REVISION_APPROVAL`; `AADHAAR NO` (formula-driven) + `ACTIVE_FOR_PAYROLL` on `REVISION_HISTORY`.
  - `OLD_SALARY_STATUS` has **no destination column** in `REVISION_HISTORY`/`REJECTED_HISTORY` — by design. It's guardrail-only and is silently dropped when a row is copied out (header-mismatch on the approved path, positional-truncation on the rejected path), then erased along with the rest of the row on delete. Safe *only* because it's the **last** column in `REVISION_APPROVAL` — inserting it mid-sheet would misalign every later column when copying into `REJECTED_HISTORY` (that copy is a raw positional slice, not header-matched).
  - `revisionApprovalCore_` now **returns** `{ approvedCount, rejectedCount, held: [{idNo, name, reason}] }` from every exit point (previously returned nothing).
- `WebApp_Router.gs` — `_callWebApp_(action, ss)` POSTs `{action, spreadsheetId, requestedBy}` to `SALARY_REVISION_WEBAPP_URL`. `doPost(e)` validates caller against the action-specific authorized email, dispatches to `submitForApprovalServer_`/`revisionApprovalServer_`. **No `doGet` exists in this module** — only `doPost`. `_callWebApp_` displays the returned `message` via **`ui.alert()`** (changed from `ss.toast()`), since this function runs client-side in the caller's own session (hrassist for Submit_Approval, nazneen for Revision_Approval) and is the only place a real dialog can be raised for a Web-App-routed user — the server handlers have no UI to pop from. This is a shared-function change: it affects both flows, not just Submit_Approval's.

## Access control

- `OWNER_EMAIL_ = 'pmo@butlerleather.com'` — runs core functions directly, unrestricted. Gets a `ui.alert()` for blocked/held rows via `_showBlockedAlert_()` (Submit_Approval) / `_showHeldAlert_()` (Revision_Approval).
- `HR_ASSIST_EMAIL_ = 'hrassist@butlerleather.com'` — may submit, routed via Web App. Blocked-row details arrive folded into `submitForApprovalServer_`'s returned `message`, shown via `_callWebApp_`'s `ui.alert()`.
- `NAZNEEN_EMAIL_ = 'nazneen@butlerleather.com'` — may approve/reject (routed via Web App), and is the notification recipient for approval requests. Held-row details arrive the same way, via `revisionApprovalServer_`'s message.
- All other callers blocked with a toast "You are not authorised...".

## Non-obvious patterns

- Header normalization via `norm()` (trim/collapse-space/uppercase); ID normalization via `normId()` also unifies various Unicode dash characters to `-` — worth knowing if `ID.NO` matching ever silently fails.
- Column-existence guard pattern throughout: builds a header→index `Map`, explicitly throws if a required column is missing, rather than failing on `undefined` later. Both guardrail additions follow this same convention for their new required columns.
- `getLastNonEmptyInColumn_()` finds append position in `REVISION_HISTORY`/`REJECTED_HISTORY` — same "don't trust `getLastRow()`" caution as elsewhere in this codebase. **This now also applies to reading `REVISION_HISTORY` for the reissue-detection index**: `REVISION_HISTORY`'s `AADHAAR NO` column is a whole-column `MAP()` spill formula (`=MAP(A2:A, LAMBDA(...))`), which stamps `""` into every row down to the reference's end — a formula-produced `""` still counts as "content" for `getLastRow()`, so `dst.getLastRow()` would report a hugely inflated row count. `revisionApprovalCore_` instead derives its row count via `getLastNonEmptyInColumn_()` scoped to `ID.NO`, immune to the spill.
- `_fetchEmployeeMasterIndex_()` (defined in `Submit_Approval`) is called directly from `Revision_Approval` with no re-declaration — both files are bound to the same spreadsheet/Apps Script project, so top-level functions are globally shared across files in this module.

## Dependencies

- `ACTIVE_FOR_PAYROLL` on `REVISION_HISTORY` rows is consumed downstream by [payroll-generator/](../payroll-generator/CLAUDE.md) (`REVISION_HISTORY` tab, read by both Get Payroll Data and Validate Payroll stages via `pickRevisionAsOf_`) — no direct code coupling exists in this module's own files, only shared spreadsheet state.
- **Employee Master** (`1yqQ-edwQzZd0pAlaXCAAZt88MbsHfCf4hCcxti4ojCw`, GID `1874110664`) — new dependency, read-only, via `_fetchEmployeeMasterIndex_()` for the duplicate-Aadhaar and reissued-code guardrails. Requires `ID.NO`, `NAME`, `STATUS`, `AADHAAR NO` headers and the Sheets Advanced Service enabled on this project.
